# 补丁后的受控服务激活

0.16 增加独立的服务激活计划、明确批准、持久任务和验证回执。安装了修复包但进程仍映射旧库时，原补丁任务继续保留 `installed_restart_pending`；服务激活使用新身份，不改写原安装结果或安全暂停。

0.17 增加激活后的独立暂停恢复；它与服务重启分开批准。两台授权 VPS 的新 KVM 已分别完成[客户端 HTTP 确认层实验](ACTIVATION_RECOVERY_LAB.md)和[Root 业务返回层故障实验](ACTIVATION_RECOVERY_RECEIPT_LOSS.md)，两份身份也与下文 0.16 实验分开记录。常驻控制台已另行[升级至 0.17](PERSISTENT_UPGRADE_017.md)，原目标 Root 入口与激活权限保持。

## 执行边界

控制端和 Root 分别配置许可，默认关闭。仅能从原补丁、当前旧库映射及实际 systemd 单元推导目标；API 不接受任意 unit、Shell、环境变量或重启主机参数。当前一次只允许一个服务，手动模式可以预览，半自动模式必须批准具体计划。选择全自动模式不创建服务激活授权。

计划绑定原任务及安全账本摘要、当前包版本、PID/starttime/cgroup/可执行文件、单元配置与管理器环境摘要、两侧策略及模式修订，五分钟后失效。批准前和实际执行前再次核对。SSH、网络及容器基础设施等关键服务拒绝；`dbus.service` 只在明确标为 `controlled_lab` 且两侧都有例外许可的实验环境支持，不作为生产通用重启能力。

执行器保留单次批准和重启意图，使用独立 systemd worker，与包任务互斥并持有真实 APT/dpkg OFD 锁。单元取证经固定 PID1 私有通道读取已存在的属性，不通过连接系统 D-Bus broker 隐式启动服务。运行依赖和固定 RPC 见[安装入口](../deploy/vulnerability/README.md)。

Debian 12/13 的一次性验收入口见[guest 实验](../tests/activation_lab/README.md)。2026-10-30 原生 CLI 阶段两组各通过 31 项检查；后续真实 Web 阶段在两个发行版的 Chromium、Firefox、WebKit 六个新 guest 上各通过 18 项检查，覆盖正式页面批准、真实 API/SSH/Root 验证、证据下载、控制端重启后重新登录及原任务/暂停保留。历史补丁/vendor finding 仍是合成前置件，没有进行 Debian APT 修复；完整版本、耗时、证据与清理见[实现记录](IMPLEMENTATION_NOTES.md#debian-1213-真实-web-批准闭环2026-10-30)。

## 验证与持续观察

重启之后必须同时取得新进程身份、精确修复版本、无旧库映射、原 finding 的官方复扫、登记 HTTP 条件、无重启待办及真实新修复 SSH 连接。确认来自 Root 的实际连接证据，客户端不能提交 `verified=true`。

回执未知时只查询同一个激活 ID，不重复提交或重启。控制台 GET 和证据下载读取缓存，不借页面刷新执行动作；后台通过独立修复连接跟进同一任务。控制端重启后保留身份与通知去重。

已验证激活通过独立 `service_activation` 事件触发漏洞观察复扫，队列 `job_id` 为空，另外保存 `original_job_id` 和 `activation_id`，不把新扫描归到原补丁任务。新 Root 策略产生的新观察范围如果从未记录受影响状态，不补造“已解除”告警；激活回执通知、复扫结果和部分覆盖事件各自展示。当前通知仍在控制台，没有外部推送。

原自动安全暂停不会因激活成功、标记已阅或切换模式自动清除。0.17 可在已同步的手动模式下，从“核对激活后的暂停恢复”建立独立预览，并明确批准这一条实际原暂停；它不重新安装或重启服务。只有原自动 pending 任务、已验证激活、精确暂停原件、当前包/进程/复扫/健康及新 SSH 证据全部一致，才允许对账。半自动父任务和缺失安全状态不能补造暂停或恢复权限。

该流程使用 `/api/activation-recoveries`，未知结果只查询原恢复 ID。Root 回执和当前安全快照核对完成后，控制端才会标为 `verified/local_released=true`；原安装任务、激活、授权与已用配额保持，模式不会切回自动。旧 schema 1 原任务恢复仍要求原任务已经 verified。完整条件和 API 见[暂停后的人工恢复](RECOVERY.md)。

证据导出类型仍为 `opsark-service-activation-evidence`，使用 `tools/verify_activation_evidence.py` 离线核对；旧漏洞证据 CLI 仍不解析此类型。激活导出只证明其已保存事实，不能代替独立恢复批准。

独立复扫关联未完成或缺观察时，导出保持 incomplete；只有扫描/观察 ID、作用域、时间和原件绑定一致，才可标为 internally_consistent。该状态不等同于供应商漏洞覆盖。Debian 实验的原父补丁仍为 synthetic_fixture；复扫中的包、进程、映射及健康检查为实际原生读取，官方漏洞判定为 not_evaluated，coverage 保持 partial，不伪造“漏洞已解除”事件。详情见[实验入口](../tests/activation_lab/README.md#激活后的独立原生复扫与导出)。

## 0.16 两台隔离环境的实际结果

本轮只使用两台已授权 VPS 内新建、不公开端口的 Ubuntu 24.04 x86_64 systemd guest。guest 共享宿主内核，不是独立虚拟机；结果不证明物理宿主漏洞清除。环境准备阶段的旧包、旧进程设置与产品的补丁安装、服务重启分开计数。

| 路径 | 父补丁来源 | 产品激活结果 |
| --- | --- | --- |
| CN | 一次真实模型请求被结构校验拒绝，原失败与预算保留；随后独立明确批准 Expat 单包补丁 | 一次真实 Web 预览、一次勾选批准、一次服务重启；激活 verified，通知一次 |
| Intl | 一次真实模型分析完成，受限自动安装 Expat，因旧库映射保持 pending | 管理器环境漂移时拒绝且不重启；恢复环境后新计划仅批准一次，实验客户端丢弃真实接受回执，产品经原 ID 查询由 unknown 到 verified；该激活通知两次 |

两侧都将 `libexpat1` 从 `2.6.1-2build1` 升至官方 `2.6.1-2ubuntu0.6`，产品各安装一次、重启服务一次。原 11 条 CVE 对应判断均复扫为不受影响，旧映射为零，登记 HTTP、新 SSH 与专属观察复扫通过。两份原父任务仍为 pending/revision7，Intl 原自动暂停、CN 安全状态确实缺失的 sentinel 分别保持。CN 的 AI 失败不能计为 AI 自动修复成功。

Intl 的回执丢失由实验客户端包装器在确实收到 Root 回执后丢弃，用于验证查询与防重放，不声称发生了真实链路断线。CN 的历史旧包准备保留了结构化映射、inode 与后续同 inode 的原始 deleted 映射，未留存同阶段全部 raw maps/库文件；该证据限制不回填。两侧完整取证与收尾原件在私有实验档案保留。

CN 原失败 AI 的单份导出仍因原候选历史快照未留存而显示 incomplete；来源、输入及模型等已保留项的核验分别通过，前期数据库快照另存，不能把当前候选补成历史原件。最终修复包的 `.deb` 未作独立成员重算，其安装依据为原生 APT 事务及 SHA 回执。Intl 另保留当前库的原始磁盘 stat/SHA 与新映射交叉记录；CN 保留新非 deleted 映射及原生运行时结果，未留独立当前库 stat/SHA 原件，两侧证据层次分别标明。

控制台镜像以 `85d181a` 构建，其应用文件与最终 `3050cbb` 逐字相同；新增 guest 的十个 Root 运行文件及安装器、两个 worker unit 按最终源核对。物理宿主原九文件入口与权限保留。Linux 原生锁、真实 PID1 私有属性读取及跨平台回归见[验证记录](IMPLEMENTATION_NOTES.md)，小型 VPS 的资源数据与尚未验证的最低规格见[资源实测](RUNNING.md#资源占用与小型-vps)。

## 0.17 第一台：客户端确认层实验

本轮在一台授权 VPS 的新 Ubuntu 1 核/1 GiB KVM 内，以真实自动 Brotli 补丁产生 pending7 父任务和实际暂停。在 assisted2 下明确批准一次普通服务重启，激活达到 verified6；随后切到 manual3，独立批准恢复并完成本地释放。产品安装、服务重启和恢复各一次，Root/控制端已用量均保持 `1/1`，原父任务、激活、策略、grant 和模式原件没有被恢复流程改写。

客户端 HTTP 确认响应被实验丢弃后，只查询原恢复 ID。真实控制端应用重启及约 120 秒自然迟到轮询没有重放或重新暂停；重新登录的查询为 0 POST、1 GET，1440/390 视口均留证。165 文件及十库快照的独立审核为 621/621，两个真实 `.deb` 的三个库成员与新旧映射也分别核对，清理已完成。

完整证据及限制见[激活后的独立暂停恢复实机记录](ACTIVATION_RECOVERY_LAB.md)。本例只丢弃浏览器 HTTP 确认，不把后续第二台的业务回执故障注入算入其历史。本轮资源分析仍为 `partial`，容量结论继续使用既有独立[容量验收](CAPACITY_ACCEPTANCE.md)。

## 0.17 第二台：Root 业务回执未交给控制端

第二台的新 Ubuntu 1 核/1 GiB KVM 完成真实自动 Brotli 安装、普通服务激活和独立恢复各一次。故障层在真实 SSH 返回 verified 回执并通过产品校验后，隐去该业务返回值并抛出 `UnknownPatchResult`；Root 已完成恢复，控制端仍确有 unknown、空回执和活动 latch。未知状态经历两次真实控制端重启仍未重放，随后通过一次原恢复 ID 的原生 status 完成对账；对账前后共三阶段十库冷取证。

原父任务 pending7、激活 verified6、三份 Root raw SHA、服务 PID `13797`、usage `1/1` 和 manual3 保持。14 份 Root 交付文件与单独测试层分别核对；299 文件归档独立复核 1180/1180，312 份读取原件 SHA 不变，清理已完成。完整证据见[第二台业务回执故障验收](ACTIVATION_RECOVERY_RECEIPT_LOSS.md)。

这不是浏览器 HTTP 丢弃或物理 socket 丢包检测，也没有开放全自动解除暂停。常驻实例在实验前/后/清理后仍为 manual14，配置、权限及 18 张既有表一致，原 Root 九文件入口和旧容器保持；没有把实验授权合并进去。本轮约 40 分 40 秒资源记录虽无 OOM/swap，仍为 `partial`，不新增容量通过。
