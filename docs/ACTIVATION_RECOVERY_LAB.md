## 范围与真实前置件

在这台授权 VPS 内新建独立 KVM 客体，配置为 **1 vCPU、1024 MiB RAM、无 swap**；客体实际可见约 961.5 MiB 内存。Ubuntu、Docker、控制台、受限 SSH/Root 入口、Nginx 和普通 Brotli 测试服务均位于这份客体预算内。浏览器在操作者 PC 上运行，客体没有运行本地大模型。

此例使用新的身份、角色凭据、数据库和原生账本，不复用旧容量实验的任务，也没有通过 SQL 填入成功状态。Root source pin 为 11 份运行代码，交付文件共 14 份，包含安装器及两个 worker unit。

环境准备通过签名 Ubuntu APT 将单个 `libbrotli1` 设置为受影响旧版本 `1.1.0-2build2`；它单独计为实验准备。之后由产品依据真实 **USN-8956-1**、原生包状态和受限自动授权，将该包升级至官方修复版本 `1.1.0-2ubuntu0.1`。没有操作者调用安装 POST 代替自动执行，也没有模型分析或模型调用。

普通 `capacity-brotli-fixture.service` 实际加载 Brotli encoder、decoder、common 三个库，对固定本机健康数据执行压缩和解压。它不是客户业务、数据库或漏洞利用流量。该轮不涉及关键服务重启例外。

执行条件及 API 合同见[人工核验与恢复](RECOVERY.md)和[受控服务激活](SERVICE_ACTIVATION.md)；完整小规格 VM 的容量方法及既有结果见[容量验收](CAPACITY_ACCEPTANCE.md)。此前案例的资源水位、两台结果和清理状态不能计入本轮。

## 拒绝、连接异常与实验时钟

第一次激活预览返回 **409**，错误正文及其 SHA 均保留。随后原生检查确认：激活计划、原生激活记录及控制端激活记录都为零，原父任务及暂停字节不变，fixture 没有被重启。后续只读取证观察到除 fixture 外，`packagekit.service` 也曾映射旧 Brotli 库；它在 **00:52:08 UTC 自然退出**，之后快照只余 fixture。没有通过额外重启 PackageKit 来凑准入。

409 正文是通用拒绝说明，不能将后续观察反推为第一请求的唯一内部原因。现场变化后取得的新预览为 200，成功激活阶段只有一次预览 POST、一次批准 POST；首次拒绝仍计入真实预览总数，不能抹掉。

第二次浏览器操作前还发生过一次 **GET-only 连接 reset**。对应审计中变更请求为空，没有安装、激活或恢复 POST，不能将它记为已提交动作或回执丢失。一份诊断异常日志涉及短期实验访问令牌，该令牌随后已作废并轮换；SSH 角色密钥、模型及个人真实密钥未受影响。本文不附令牌、认证头或私有凭据。

客体尝试 Ubuntu IPv4/IPv6 NTP 时未收到 NTP 包，不能记为同步成功。操作者随后通过已建立、限定为该 VM 的实验管理员 SSH 连接，将**仅此客体**的时钟对齐 PC；测得往返时间上限约 0.36 秒。该动作明确记录为实验环境准备，没有修改物理宿主时钟、产品的时间/有效期检查或原父任务记录，也不作为产品自动时钟修复能力。

## 丢弃的是客户端 HTTP 响应

恢复 UI 实验在服务端已处理批准后，**故意丢弃浏览器收到的客户端 HTTP 确认响应**。操作审计明确记录 `client_http_acknowledgement_dropped=true`，同时 `root_or_controller_receipt_loss_injected=false`。

因此本例证明的是：浏览器没有拿到确认时，界面仍能使用同一恢复 ID 查询已持久保存的结果；它不证明 Root 到控制端的回执丢失。Root 和控制端的正式回执均未被丢弃，也没有伪造真实链路故障。恢复审计记录一次预览 POST、一次明确批准 POST，随后 GET 原恢复 ID；没有通过新 ID 重发批准。

激活成功阶段没有注入客户端响应丢弃。执行阶段的激活与恢复结果均记录 1440/390 宽度、无横向溢出和空 `page_errors`。

后续在新浏览器会话中重新登录，只查询原恢复 ID。最终 query-only 原件 `query-fa58300acbd040ca8b415e4f519fc107` 记录 **0 次预览 POST、0 次批准 POST、1 次 GET 原恢复 ID**，结果仍为 `verified`。完整 after 核对通过，原父任务、模式、grant、额度和恢复没有改变；1440/390 宽度均无横向溢出、无页面错误，390 图及布局原件完整保留。

此前查询实验发生过定位器竞态、CSP 影响截图以及后续收尾 GET reset，失败原件均保留。这些属于私有浏览器/快照 harness 的问题，没有触发新的批准或原生动作。仅在私有快照 GET 使用 `Connection: close` 后实测读取成功，没有修改产品传输配置，也没有确定这些连接异常的真实根因。

## 真实控制端重启及迟到观察

恢复完成后，实验对同一个受限控制端容器执行了一次真实应用重启，保留相同镜像、数据、目标和授权。控制端 PID 从 `15112` 变为 `17596`；fixture PID 保持 `15941`，没有再次重启服务或 VM。

重启前后 `recovery-verification` 的完整核验对象相同：原父任务、激活及恢复原始 SHA，Root/控制端策略 SHA，授权 ID，使用量，fixture PID，安装/重启/恢复计数，以及 Root 暂停和本地 latch 状态均一致。此后没有伪造旧快照回放，而是让后台自然继续读取原 pending 任务和远端安全状态。

在重启结果记录后约 **120 秒（实测 119.86 秒）** 的最终核验中，仍为 manual3、Root 未暂停、本地未 latch、Root/控制端使用量 `1/1`，原安装、激活、恢复各一份，模型调用为零。本轮最终内核 OOM 计数和记录均为零；这段观察不是长期稳定性或并发容量证明。

下载端逐项核对归档成员、大小和 SHA；十库的原始 manifest 保留，全部 SHA、`quick_check`、`foreign_key_check` 通过。独立标准库审核器最终 **621/621 通过**，错误、失败和缺件列表为空；重新计算的 **170 份原件 SHA** 均未变化。两个 `.deb` 的实际成员、三库新旧二进制与原始映射/inode、原任务和回执、Root14 源码及数据库关联均单独核对。检查数是一致性项目数，不是修复率；审核器没有重新连接服务器，也不将 SHA/Git blob 校验当作来源认证或独立 APT 索引签名验证。

独立审核器首次还误拒绝了 `.deb` 内合法 tar `.` 目录标记。随后只修正 reader 对精确目录标记的处理，保留初次报告，没有修改归档或原件。最终重跑结果为 `review-final-rerun` 的 621 项通过。
