# 0.9.1 SSH 回执完整性修复与实机验证

更新日期：2026 年 10 月 29 日。实验时间统一使用 UTC。

## 故障证据

第一台授权 VPS 的扫描曾反复显示 `unavailable`，而远端已经生成约 345 KB 的扫描文件。2026-10-28 的实际受限 SSH 连接记录显示：控制端接收 196,608 字节时看到退出码 0，但 `eof_received=false`、通道仍未关闭。此时 stdout/stderr 队列暂时为空，旧代码提前退出接收循环；JSON 在字符 196,604 附近截断，因而未进入补丁缓存和定期观察存储。

这次失败已定位到接收循环，不能继续把这份故障记录解释成服务器没有生成结果，也不能用旧策略范围的缓存替代当前证据。

## 修复边界

`patch_client.py` 与只读采集器 `collector.py` 现在分别检查：

1. 收到远端 EOF，或底层传输仍有效时的正常通道关闭。
2. stdout 与 stderr 都已排空。
3. 退出状态已就绪，随后取得明确退出码；只有正常成功码才作为成功结果。

退出码不再代替输出完成。没有 EOF 的底层断线，即使已经读到完整 JSON 和退出码 0，也不能证明响应完整：只读请求返回失败；修改请求继续保留原任务 ID 和未知结果，不重发安装。EOF 先于退出状态到达时，仍受原绝对期限约束，不调用可能无界等待的状态读取。

原有主机密钥核验、独立修复密钥、固定远端入口、请求与输出预算、stderr 预算和绝对期限没有放宽。1 MiB 修复响应及 4 KiB stderr 限制仍有效；正常延迟尾包也须计入预算。定期观察仍按既有规则在完全读取失败后 300 秒重试，没有增加修改请求自动重试。
