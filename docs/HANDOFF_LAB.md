# 客户交接摘要实机验收

2026 年 11 月 4 日，在第一台授权测试机的新建 Ubuntu 24.04 guest 上运行 `bede88c` 的临时控制端。guest 运行原生 OpenSSH、systemd、APT 和 Nginx，使用独立私网、专用 SSH 角色和全新的账本。guest 没有公开端口或宿主挂载；它是共享宿主内核的隔离容器。本轮没有连接常驻控制端或第二台测试机，也没有启用模型、持续观察或自动授权。

## 审批、安装和原任务对账

1. 原调查经真实只读 SSH 采集。日志和登记的 Nginx HTTP 响应含不同的人工标记，便于对照客户导出是否包含原文。
2. 以半自动模式人工批准一次。Root 依据 [Ubuntu USN-8956-1](https://ubuntu.com/security/notices/USN-8956-1)，将实验内唯一获批的 `libbrotli1` 从 `1.1.0-2build2` 升级至 `1.1.0-2ubuntu0.1`。APT 历史确认该升级执行一次，同一漏洞复扫通过，并经新的受限 SSH 连接验证。
3. 故障注入只针对提交连接：先核对 Root 原审批、任务和提交回执均已持久保存，再由 guest 私网中继执行 TCP abortive close。控制端实际报告连接被对端重置，保存 `unknown`；未留到独立抓包证据。本轮没有重发安装。15 次状态查询均使用同一个原任务 ID，最后取回 `verified`。
4. 在对账和补丁验证之后，另发起同一登记范围的只读调查。新的 HTTP 请求得到 `200`，正文匹配，1/1 项登记检查通过。

## 客户导出对照

| 导出时机 | 原任务 | 业务验收 |
| --- | --- | --- |
| 断线后、对账前 | 已批准，结果未知，待对账 | 待验收 |
| 查回原任务后、业务复验前 | 已对账，补丁任务验证通过 | 待验收 |
| 关联后续独立复验 | 原任务和对账记录保留 | 登记业务复验通过（1/1） |

即使已生成合格复验报告，不选择关联该报告时，导出仍与原「待验收」版逐字节一致。三份实际下载均通过检查：不含内部报告中确认存在的假日志和 HTTP 正文标记，也不含测试主机标识、地址、域名、路径、内部任务/报告 ID、策略摘要或临时访问令牌。未认证的下载请求被拒绝。客户摘要只证明已登记项目的本次检查结果。

验收后已清理临时 guest、控制端、网桥、中继和实验凭据。测试机上另外 18 个容器的身份、镜像和运行状态与实验前一致。没有保存原始日志副本作为客户交接材料。

[验收驱动](../tests/handoff_guest_acceptance.py) 使用临时控制端的 loopback HTTP API。它要求独立的 `controlled_lab` 目标、真实旧包和已登记的只读 HTTP 检查。故障中继由实验环境单独提供；`--submit-barrier-dir` 用于在单次批准前协调中断。驱动只保存经过隐私检查的 Markdown 和结果计数，不复制原始日志、内部报告或凭据。

## 复验失败和证据不完整

同日在新的隔离 guest 上完成一次真实补丁安装和原任务对账，随后用相同的主机登记、预期状态和预期正文分别发起只读 SSH 复验。对照只改变实验 HTTP 端点的响应。

| 实际采集 | 客户摘要 |
| --- | --- |
| HTTP 200，已完整采集响应，实际正文不符合登记条件 | **复验未通过** |
| 上游延迟响应，curl 达到 4 秒时限并返回 28，未取得可判定的 HTTP 状态和正文证据 | **待验收** |

两份摘要都保留已验证的原补丁结果和对账记录。重新导出此前选定的通过报告以及未关联复验的摘要，文件均与原件逐字节一致。两份新增下载中未发现原始日志、成功或失败响应的正文标记、超时报错原文、测试主机信息、内部任务或报告编号及凭据。

验收驱动可用 `--negative-recheck-barrier-dir` 和 `--failed-body-marker` 启用这组对照。实验环境依次切换 `mismatch` 和 `timeout`，各在确认端点状态后通知驱动开始真实采集。实验完成后清理临时环境和凭据。

## 多项业务检查结果不一致

在新的隔离 guest 上登记三项只读 HTTP 检查。真实补丁安装并完成原任务对账后，先复验三项均正常的端点，再改变其中两项的响应。每组都发起独立的 SSH 采集，使用相同的登记条件和原任务。

| 三项检查的实际采集结果 | 客户摘要 | 符合登记条件 |
| --- | --- | --- |
| 三项 HTTP 200，正文均匹配 | **登记业务复验通过** | 3/3 |
| 一项通过，一项 HTTP 200 但正文不匹配，一项达到 4 秒请求时限 | **复验未通过** | 1/3 |
| 两项通过，一项达到 4 秒请求时限 | **待验收** | 2/3 |

三份下载均通过隐私检查。摘要保留原任务对账和本次复验结果，客户可见的信息限于已分类的状态、时间和计数。两份混合结果保存后，重新导出此前关联的通过报告和未关联复验的摘要，文件均与原件逐字节一致。

在验收驱动中设置 `--mixed-recheck-barrier-dir` 和 `--failed-body-marker` 可启用这组对照。三个检查 ID 为 `lab`、`auxiliary`、`third`。实验环境依次准备 `mixed-failure` 和 `mixed-pending`，再通知驱动采集。

## 恢复业务检查后复验同一任务

上轮实机任务库随临时环境清理，保留了脱敏导出。为避免重新执行补丁，本轮只读隔离控制端预置了一条模拟的已验证历史任务。摘要中的审批、补丁执行和对账来自这条模拟记录，失败、超时和恢复后的业务复验来自本轮真实 SSH 和 HTTP 采集。控制端未配置修复目标，guest 未安装修复入口，验收期间的软件包清单一致。控制端记录了五次只读调查请求和零次修复提交。

同一个任务先关联 1/3 项符合的「复验未通过」报告，再关联 2/3 项符合的「待验收」报告。恢复实验 HTTP 端点后，重新采集三项检查，全部返回登记的 HTTP 状态和正文，新摘要显示「登记业务复验通过（3/3）」。恢复前的报告仍可按原 ID 查询，旧摘要可逐字节重现。重启临时控制端后，五份报告仍可查询，五份摘要重新导出的字节均一致。

验收驱动用 `--existing-report-id` 和 `--job-id` 指定只读隔离环境中的已有任务和原调查。第三个阶段通过 `restored.ready` 与 `restored.armed` 同步。客户导出检查覆盖原始日志、HTTP 正文、超时报错、主机信息、内部编号及临时令牌。实验结束后保留不含凭据的私有离线历史，清理运行环境和临时凭据。

## 从界面发起真实 SSH 复验

在授权测试机的新隔离环境中部署 `b67623a`，用 Chromium 登录实际控制台。控制台只通过本机 SSH 隧道访问。旧离线档案保留原样，新 guest 使用独立 SSH 身份，并预置一条模拟历史任务供三轮复验共同关联。此处的审批、补丁执行和对账来自模拟记录。每轮业务证据都经真实 SSH 采集。

每轮从交接窗口点一次「运行只读复验」。浏览器和服务端均记录了三次复验请求，均成功保存，并且没有补丁提交。软件包清单在验收前后一致。界面先显示「复验未通过」1/3，再显示「待验收」2/3，最后在三个 HTTP 端点都符合登记条件后显示「登记业务复验通过」3/3。恢复后重新打开窗口，仍能分别选择失败和待验收报告，两份重下载的 Markdown 与首次下载逐字节一致。

三个下载件均核对过日志标记、HTTP 正文、超时报错、主机信息、内部编号和临时令牌。可用[浏览器验收驱动](../tests/handoff_browser_guest_acceptance.py)复现浏览器操作。驱动连接已准备好的隔离控制台，并通过阶段标记等待实验端点切换。

## 真实补丁任务到浏览器复验

2026 年 11 月 5 日，在授权测试机的隔离 guest 中人工批准了一次 `libbrotli1` 升级。中继确认 Root 已保存原审批和任务回执后，重置该次 SSH 提交连接。控制端先记录结果未知，再经新连接查询同一任务。精确安装版本、同一漏洞复扫和新的受限 SSH 登录均通过。Root 审计记录一次提交，APT 历史记录一次升级。

在同一控制端移除临时修复密钥并关闭修复配置后，保留原 SSH 登记、任务和数据库。用 Chromium 从交接窗口发起三次真实只读复验，依次得到「复验未通过」1/3、「待验收」2/3 和「登记业务复验通过」3/3。恢复后重新选中两份旧报告并下载，内容与首次下载逐字节一致。业务复验期间修复请求为零，原审批、原生回执、任务记录和包清单保持一致。

## 目标机侧业务复验回执

在授权测试机另建隔离控制台和 Nginx 目标，使用实际受限 SSH 安装器。隔离控制台预置一条合成的审批、补丁验证和原任务对账记录。四轮业务检查均使用真实 SSH 和 Nginx 反代，所有复验绑定同一任务。

| 业务路径响应 | 客户交接摘要 | 符合项 |
| --- | --- | --- |
| 上游断开，Nginx 返回 502 | 复验未通过 | 1/2 |
| 错误上游返回 200 | 复验未通过 | 1/2 |
| 上游超时 | 待验收 | 1/2 |
| 正确上游恢复 | 登记业务复验通过 | 2/2 |

静态路径始终通过。每条新回执只保存检查结果和绑定字段，客户导出不包含响应正文、目标路径或证据摘要。恢复后可选取全部旧回执，旧摘要逐字节一致。原报告、原任务账本及其他数据库内容保持一致，模型探针未收到请求。

五份客户摘要均通过敏感字段核对。原调查、三份复验报告、任务账本及 Root 保存的原任务、计划、审批和首次提交回执保留在无凭据的私有离线归档中。可用验收驱动的 `--stop-after-reconciliation` 将原任务移交浏览器阶段，再用浏览器驱动的 `--require-native-receipt` 核验原生回执。
