# 小规格 VPS 容量验收

验收日期：2026-10-31（Asia/Shanghai）。原件时间使用 UTC。此记录补充[组件资源测量](RUNNING.md#资源占用与小型-vps)，不能用一次实验发布适用于所有业务的最低配置。

## 完整 VM 的范围

本轮在两台已授权测试 VPS 内分别建立独立 KVM 虚拟机，明确配置 **1 vCPU、1024 MiB RAM、无 swap**，不使用共享宿主内核的 systemd 容器代替整机。QMP 实际内存/CPU/KVM 状态、唯一 UUID、客体独立 boot-id、系统可见约 961.5 MiB 内存及无 swap 共同留证。OS、Docker、控制台、受限 Root 入口、Nginx 和测试工作负载全部位于这份客体预算内。

Ubuntu 24.04 官方云镜像选用固定的 `release-20261017`，先核验 cloud-image keyring 的签名和 SHA256，再启动；实际镜像 SHA 为 `04e8f2461a16a44e78a370284471f29616cdd9baf1893df25807b71f985b6c94`。工具容器仅获得 `/dev/kvm` 和本次独立目录，采用只读根、cap-drop、no-new-privileges，没有 privileged、host namespace 或 Docker socket。物理宿主不安装 QEMU 或其它软件包，既有控制端和 Root 权限保持。

客体采样使用[只读采样器](../tools/capacity_guest_probe.py)：系统 Python 3.12 标准库，2 秒间隔，记录整机内存、CPU、PSI、OOM/swap 计数、磁盘及自身 RSS。采样器在 cloud-final 阶段开始，早期开机未逐秒采样；硬件预算自启动起生效，整个 boot 的内核 OOM 日志另行核对。虚拟机检测本身不等于预算证明，数据仍需与外部 QMP 证据关联。

控制台限制 256 MiB、0.5 CPU，其 cgroup 是组件数据；Root 扫描和包管理器位于客体系统中，不能只用控制台 RSS 代表整机开销。物理机的 QEMU cgroup 包含客体 RAM 页和管理开销，另列，不能加成客体进程 RSS。浏览器运行在使用者 PC，测试没有在 VPS 内运行浏览器或大模型。

## 第一次探索保留为未通过

CN 的完整 VM 在 1 GiB 内完成源码构建、启动与真实 Ubuntu 扫描，但沿用旧容器实验的 D-Bus 准备动作后，`systemd-logind` 登录会话依赖未恢复。日志记录 `login1` 激活及 `pam_systemd` 会话注册 25 秒超时。模式响应晚到后只查询原修订，实际补丁规划被 503 阻止；原生计划、安装任务、激活和 AI 请求均为零。

没有禁用 PAM、人工恢复服务后冒充原产品闭环或扩大产品超时。原失败、旧包/映射/二进制、十库和诊断已保留，虚拟机停止并清除临时凭据及秘密虚盘。这项结果不计入修复成功；共享内核容器的关键服务对照不能推广为完整普通 VPS 的处置支持。

1607 个样本约覆盖 54 分钟。该次扫描阶段可用内存最低约 **2.19 MiB**，虽然 OOM 为零，仍表明余量不足；构建阶段最低可用约 461 MiB。低水位属于整个扫描阶段，不单凭它归因某一个子进程。

据此给可选 Ubuntu Pro 采集补上固定资源边界：提供方导入前限制虚拟地址空间至多 256 MiB，保留继承的更严限制，并禁用 core dump；不在多线程调用者使用 `preexec_fn`。内存分配失败、预算无法建立和信号终止分别保留静态覆盖缺口，独立 USN 依据继续评估。它是地址空间上限，包含解释器和映射，不是 RSS 预留；合法的全量数据也可能因此无法完成，不能报告“零漏洞”或整机安全。

## 普通服务的真实修复路径

第二台新 VM 使用独立 UUID、凭据、账本和普通 `capacity-brotli-fixture.service`，没有 D-Bus、logind 或 PAM 操作，也没有关键服务例外。该服务实际加载 Ubuntu 的 Brotli 三个库，对固定本机健康数据执行压缩和解压；Nginx 为单独的 loopback 静态站点。工作负载是明确的测试环境，不是客户网站、数据库或恶意漏洞利用。

源码冻结为 `97f1cf5`；应用文件与 `5e207d8` 相同，新增 Root 采集预算在正式入口生效。镜像确实在该 1 CPU/1 GiB VM 内从源码构建，不是外部构建后仅导入。正式控制台、Root13/readonly3、真实 SSH、官方 USN 和原生 APT 均参与，没有 SQL 填充父任务或合成漏洞判定。

## 这一档规格的观测值

普通服务 VM 自 cloud-final 开始完成一小时窗口，1799 个样本、2 秒间隔、无采样覆盖缺口；整个 boot 的 OOM 计数及内核记录均为零，swap 为零。下表为阶段采样低水位，包含操作及等待，不是各函数的独立压力上限。

| 阶段 | VM 可用内存最低观测 |
| --- | --- |
| 初始化、角色安装及 VM 内源码构建 | 472 MiB |
| 原生漏洞扫描 | 473 MiB |
| 方案与单包安装 | 319 MiB |
| 激活、查询及本机静态负载 | 282 MiB |
| 导出与备份 | 508 MiB |

整机 `MemTotal−MemAvailable` 最大采样值约679 MiB，不是进程RSS总和或精确瞬时峰值。控制台独立cgroup累计峰值约 **77 MiB**，重启前后分别留存，不能再次加到整机使用量。物理宿主QEMU cgroup约1.07 GiB，包含客体RAM页及管理进程，另列为外部虚拟化开销，不是客体应用净占用。

这支持把 **1核/1GiB作为本轮受控轻型负载已验证的一档部署规格**，仍不保证并发业务、大数据集、其它包或模型调用开销相同。旧探索与新案例的宿主、状态、负载不同，低水位变化不是严格单变量A/B因果实验，预算机制另有独立内核正反对照。

普通案例十库在控制台停后全局冻结备份；旧包、修复包和三库新旧bin/maps/stat均保留，临时凭据不导出。两套VM、本次QEMU、秘密虚盘/NoCloud种子及PC临时私钥已清理；原永久控制台、旧容器和物理Root文件/策略/模式保持。

## 验证与适用边界

普通案例的纯标准库独立核对 **106/106 通过**，缺件/错误为空：实际old/fixed `.deb`成员、三库raw文件/映射/inode、Root13、原父任务、唯一激活及新SSH、SQL/原观察关联、自然一小时日志、重建和清理分别核对。检查数是原件一致性项目数，不是修复率或来源签名；初次409正文缺件和早期开机采样边界仍保留。

采样器 43 项回归通过，原 `5e207d8` CI 十项通过。资源边界新源在 Windows 专项 85 通过、7 个 Linux 项跳过；真实 Ubuntu 系统 Python 上另有内存正反对照，CN 独立 Linux 容器两份扫描回归 **92/92 通过**，全输出与源码 SHA 保留。新 `97f1cf5` 的 GitHub Actions 因账户账单/支出上限在任务启动前被阻止，未执行 checkout 或测试，不能计为 CI 通过；没有改动费用设置。

本轮没有检验完整 512 MiB VM、长时间并发、多目标上限、本地模型、MySQL/真实客户业务、任意大包或主机重启。也没有在永久实例开启新的自动授权。容量结论只适用于这里记录的镜像、代码和负载；更小规格或更重负载需要独立验收。
