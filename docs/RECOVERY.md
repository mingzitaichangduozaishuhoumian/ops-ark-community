# 自动处置暂停后的人工核验与恢复

更新日期：2026 年 10 月 31 日。包括 0.10 原任务恢复和 0.17 激活后独立恢复；实验时间统一使用 UTC。

0.10 的流程处理原自动补丁任务已经完成验证，但控制端或 root 因回执丢失、执行超时等原因仍保留持续暂停的情况。0.17 另提供独立入口：原自动任务仍为 `installed_restart_pending`，但其对应服务激活已经 `verified`，经重新核验及单独批准后恢复。两种流程都只解除**这一条已核实原因**对应的暂停，不改写原任务历史。

**恢复不安装补丁、不重启服务或主机、不退款或重置配额、不重新签发 grant，也不切换到自动模式。** 原任务、旧暂停和恢复审计均保留。模型解释没有恢复权限。

既有控制端升级验收确认配置、授权和历史保留，本轮实验范围单独保留。当前部署可用性与独立实验结果分别记录，详见[恢复实验与交付记录](RECOVERY_LAB.md)。

## 原任务已 verified 的恢复（0.10）

原有 schema 1 恢复合同、`/api/automatic/recovery-plans` 及 `/api/automatic/recoveries` 接口保持原行为。它仍要求原自动补丁任务已经 `verified`，不会因为增加激活后恢复而接受 pending 或客户端声明的成功。

以下条件必须同时满足，控制端与 root 分别核验：

- 当前为已同步完成的 `manual` 模式，模式修订有效；控制端执行策略仍启用，允许 `os_security_upgrade`，且目标仍在允许范围内。
- 使用暂停记录关联的原自动任务，该任务已经是 `verified`，安装退出码及原管理连接验证均可核实。
- 原任务、不可变方案、包身份和安装前文件清单完整；当前实际版本仍等于原方案批准的候选。
- 软件来源、有效 APT 配置、包状态、登记服务及 HTTP 检查通过，没有重启待办；旧文件和当前文件的进程映射检查完整且没有旧映射。
- 对同一 finding 取得新鲜、完整的逐条供应商复扫证据，明确确认本条不再受影响。
- 没有其它进行中、结果未知或尚未对账的事务；批准时再次核对包状态、任务、账本、策略、暂停原因和有效期。

`unknown`、`failed`、`rejected`、等待新 SSH 验收、仍在安装或存在重启待办的原任务，不能直接通过这个入口恢复。先保留原任务继续查询和独立处置，不能把状态手工改成 `verified`。

## 已验证激活后的独立恢复（0.17）

该入口使用新的恢复身份与明确批准，激活批准不能直接用来解除暂停。原自动安装任务保留 `installed_restart_pending`，原服务激活保留 `verified`；恢复回执中的 `resolved_job` 也明确保留 pending 状态，另以 `verified_activation` 绑定实际已验证的激活。

控制端与 Root 分别核对以下条件：

- 当前为已同步的 `manual` 模式；目标启用，且当前仍有明确的 `service_activation` 包和单元许可。
- 原自动任务确为安装退出码 0、原管理连接已验证的 `installed_restart_pending`，其不可变计划和安装前文件清单仍完整。
- 激活回执已 `verified`，原任务 ID、修订、摘要、原始文件及激活计划、重启意图均与本次恢复绑定。Root 升级后仍须能核实旧回执来源，复用主机 ID 指向另一目标不能沿用旧证据。
- 本地存在活动暂停，Root 也实际存在同一原任务的 `automatic_job_installed_restart_pending` 暂停；精确原暂停原件必须与激活记录一致。半自动父任务、缺失或未暂停的安全状态都不能补造成可恢复原因。
- 当前精确包版本、有效 APT 配置、登记服务与 HTTP、同 finding 的新鲜供应商复扫、已激活进程身份及完整运行时检查均通过，无旧库映射或主机重启待办。
- 没有其它活动或未知事务。批准再次绑定当前模式修订、策略、账本、暂停摘要与五分钟预览期限，并取得预览之后建立的新 SSH 连接证据。

Root 先保存不可变回执，再对原暂停生效。控制端还须读取回执之后的新安全快照，确认目标、策略、实际暂停状态及使用量一致，才解除对应本地暂停。出现新的暂停、变化的原任务或不同进程时，旧恢复不能放行；审计继续保留。

### API 与查询语义

接口要求与其它修复 API 相同的认证，不接受临时目标、任意命令或客户端 `verified` 标记。

| 请求 | 必要输入或结果 |
| --- | --- |
| `GET /api/activation-recoveries` | 只读持久列表，返回 `enabled`、`supported_modes=["manual"]` 和 `records`；不扫描或提交恢复 |
| `POST /api/activation-recoveries/plans` | `host_id`、`job_id`、`activation_id`、`expected_mode_revision`；返回原生预览，`status=activation_recovery_prepared`，包含 `recovery_id`、`recovery_digest`、`eligible`、检查项及有效期 |
| `POST /api/activation-recoveries` | `host_id`、`recovery_id`、`expected_recovery_digest`、`expected_mode_revision`、`confirm_recover=true`；先持久保存该次批准意图，再提交一次 |
| `GET /api/activation-recoveries/{host_id}/{recovery_id}` | 查询原 ID；prepared 或已终结记录读缓存，待核实记录只查询原 Root 回执并尝试本地对账，不重发批准 |

新原生回执使用 `schema_version=1`、`kind=activation_recovery`，与旧恢复类型分开校验。控制端记录沿用下表的 `prepared`、`submission_intent`、`unknown`、`verified`、`rejected`、`superseded` 状态；只有 `verified` 且 `local_released=true` 才表示这一条本地暂停完成对账。它不表示当前所有漏洞或后续暂停均已解除。

超时、断线或控制端重启后只查询同一 `recovery_id`，不能另建 ID 猜测重试。恢复不消耗新的安装次数，也不退还原次数；当前 Root 自动 grant 缺失、到期或配额耗尽不等于恢复失败，但恢复不会因此创建新授权。模式保持手动，后续自动安装仍须另行满足全部条件。

### 0.17 的分开实机结果

第一台的[独立恢复实机验收](ACTIVATION_RECOVERY_LAB.md)记录浏览器 HTTP 确认丢弃；第二台的[业务回执故障验收](ACTIVATION_RECOVERY_RECEIPT_LOSS.md)记录 Root 返回值未交给控制端调用者。两份实验身份、故障层和结论分别保留。

源码 `ff846f8bfae3b9103b7919c997ab65c9db4fa656` 已在一台授权 VPS 内的新 Ubuntu 1 核/1 GiB KVM 完成[独立恢复实机验收](ACTIVATION_RECOVERY_LAB.md)：真实自动 Brotli 安装一次，原父任务保持 pending7 并确有自动暂停；随后在 assisted2 下独立批准一次服务激活并取得 verified6，再在 manual3 下另行批准恢复，达到 `verified/local_released=true`。原父任务、激活、策略和 grant 原件保持，Root 和控制端的每日/总使用量仍为 `1/1`，没有退款或切回自动。

实验丢弃的是浏览器收到的客户端 HTTP 确认响应；随后只 GET 原恢复 ID。真实控制端应用重启后继续约 120 秒自然轮询，未重新暂停或重放；重新登录的独立查询留有 0 POST、1 GET 和 1440/390 视口记录。**本例没有注入 Root 到控制端的真实回执丢失**，不能将该故障路径宣称为新增实机通过；它也没有开放全自动解除暂停。

第一份实验保留 165 文件、两个真实 `.deb` 和十库正式快照；独立标准库离线审核 621/621 通过，170 份读取原件的前后 SHA 不变，实验环境与临时凭据清理完成。审核、归档中断的显式续导出、首次审核器拒绝合法目录成员及复跑记录均分开保留，不能将后续第二份实验的故障注入倒写到这份历史中。

第二台在另一份 Ubuntu 1 核/1 GiB KVM 中，以打包源 `e4d8f0f`、产品运行源 `ff846f8` 完成真实自动 Brotli 安装、独立激活和恢复各一次。真实 Root `verified` dict 已经由 SSH 返回且通过原产品校验，随后独立测试 invoker 层持久留证并抛出 `UnknownPatchResult`。此时 Root 回执已 verified、实际未暂停；控制端 SQL 确为 `unknown/receipt=None/local_released=false`，本地 latch 为 active=1。

在单 ID 对账前，实验对同一控制端两次真实 stop/start；初次未知、第一次重启后未知及最终已验证状态分别完成全局停止后的十库冷取证。第二次重启后由缓存列表再次确认 unknown。VM 中该容器的宿主 PID 为 `11170 → 16286 → 16839`，unknown 和本地暂停持续保留，没有再次 dispatch 或提前查 Root 恢复 ID。随后一次原恢复 ID 的原生 status 查询才达到 verified、本地 latch=0；后续 HTTP 读取缓存不增加原生 status 计数。三份 Root 原始记录 SHA、fixture PID `13797`、usage `1/1` 和 manual3 均保持。

这项确定性故障发生在 Root 返回值与控制端业务调用者之间，既不是浏览器 HTTP 丢弃，也不是物理 socket/链路丢包检测。14 份 Root 交付文件与独立测试层分别留证，没有伪造回执或直接填写 SQL 成功状态。299 文件、2,564,997 字节归档的独立复核为 1180/1180，312 份读取原件 SHA 不变；新 VM、工具、角色密钥、秘密介质和临时浏览器入口均已清理。资源只记录约 40 分 40 秒，仍为 `partial`，不属于新的一小时容量通过。

两台的有限隔离闭环不证明所有未知故障均可恢复、全自动解除暂停或物理宿主漏洞已修复。常驻控制台的[独立升级](PERSISTENT_UPGRADE_017.md)及本轮实验前/后/清理后的核对仍保留 manual14、原配置和权限；新恢复入口继续禁用。下文 0.10 的记录只证明其原有路径。

后续补测了回执已落盘后的连接重置，以及查询原 ID 时的建连丢包。控制端重启或查询超时后继续保留未知和暂停。网络恢复后，原 ID 查询取得回执及新安全快照，才完成本地释放。归档分别记录 HTTP 查询次数和实际抵达 Root 的 status 次数。[真实 TCP 验收](ACTIVATION_RECOVERY_NETWORK.md)

## 部署前提与旧记录

`capabilities.automatic_recovery=true` 表示旧恢复入口；`capabilities.activation_recovery=true` 表示 0.17 激活后独立恢复接口和界面。能力标记不证明每台 Root 入口已经支持，也不授予目标权限。

管理员需要在没有活动或未知事务时审核升级独立 Root 入口。0.10 的 source pin 包含 `recovery.py` 等九份运行代码；0.16 增加服务激活模块，0.17 再增加独立的 `activation_recovery.py`，实际完整清单以当前交付 manifest 为准。升级改变 source/policy 摘要后，需要更新目标登记，并按原接入规则重新核对模式及绑定。安装器会拒绝穿过未决事务，不应通过强杀安装器或删除任务绕过检查。仅重建控制端容器，与升级 Root 执行器是不同操作。

新 worker 在安装前保存软件包文件清单，并把摘要绑定到原任务。旧版本任务即使曾经 `verified`，也可能没有这份证据。此时预览会列出阻碍并禁用确认；**不能在安装完成后伪造“安装前清单”补过检查**。缺失旧证据的任务不属于本恢复通道的可恢复范围，须保留暂停并由管理员另行核对。

升级、迁移或恢复备份须保留当前十个控制端数据库，包括漏洞 AI 记录，以及 `automatic.sqlite3` 中的意图、配额、暂停与恢复审计；远端原任务、恢复预览和恢复回执也须保留。0.17 实验的十库正式快照已有 SHA、`quick_check` 和外键检查记录。完整部署和备份范围见[常驻部署说明](../deploy/observer/README.md)。删除数据库或暂停文件不是恢复方法。

0.17 的新批准、恢复记录和精确原任务解析关系另存于 `automatic.sqlite3`，不替换旧恢复表。远端新增的 `activation-recovery-plans`、`activation-recovery-submissions`、`activation-recovery-receipts` 也应随原任务、激活及安全状态一并保留；不能只备份最新扫描。

## 控制台操作

1. 在“漏洞与修复”中找到暂停卡，核对目标、原任务 ID、暂停来源及原因。
2. 切到手动模式，等模式同步完成。禁用策略、未授权目标、陈旧状态或已有未决恢复记录时，不会开放新的预览。
3. 点击“核对恢复条件”。服务器只进行核验并保存预览，不解除暂停。查看版本、服务、复扫、运行时结果和 `blockers`；任一条件未通过都保留暂停。
4. 预览最多有效五分钟。核对原任务、模式修订、恢复 ID 与摘要后，勾选确认框并批准这次恢复。模式、策略、原任务或暂停发生变化时，旧确认不能沿用。
5. 查看恢复记录。只有 `status=verified` 且 `local_released=true`，才说明控制端已完成该次对账并解除对应暂停。原暂停和回执仍在审计中；继续检查当前目标是否又出现了新的暂停。

批准时，root 使用预览之后建立的新 SSH 连接再次核验。慢检查之后还会重新读取实际包状态、账本和策略，以最终决策时间判断预览是否仍有效；root 先持久保存精确回执，再改变有效暂停。控制端核对回执、原任务、当前暂停及新的远端安全快照后，才完成本地恢复。

### 结果未知时

保留服务器分配的原 `recovery_id`，只点击“查询原恢复记录”。请求超时不能证明恢复没有发生；Root 可能已经提交了恢复回执，而控制端尚未完成对账。

界面不会为未知结果换新 ID 重试确认。控制端重启或重新登录后，持久恢复列表仍可用于找回原 ID；待核实记录优先展示。查询只能读取、对账原回执，不会重新发送恢复动作或安装补丁。

Root 回执必须证明恢复在原预览有效期内完成。较晚的查询可以核对这份已完成的原批准，但不能把窗口外完成、上下文已变化或证据不足的结果改成成功。

| 状态 | 处理方式 |
| --- | --- |
| `prepared` | 只有预览，尚未批准；不会解除暂停 |
| `submission_intent` | 已持久保存批准意图，结果待核实；只查原 ID |
| `unknown` | Root 回执或本地对账未核实；保留暂停，只查原 ID |
| `verified` | 核验完成；还需同时确认 `local_released=true` |
| `rejected` | 核验拒绝，暂停保留；核对阻碍后再决定后续处置，不重发旧确认 |
| `superseded` | 目标、策略、任务或暂停上下文已变化，旧恢复未解除当前暂停；保留原 ID、旧回执及已知或未知的 Root 结果，对当前原因另行预览 |

`superseded` 不等于旧 Root 动作失败。它可以保留已经验证的旧回执，也可能记录 `root_outcome=unknown`。界面不会把它显示成当前暂停已解除，更不会因此自动创建新的恢复请求。

## 为什么任务成功后仍保留暂停

结果从 unknown 或 overdue 变成 verified，只补足了原补丁任务的证据，不能替代对“是否应恢复自动入口”的明确批准。刷新、模式切换、新扫描和新 grant 都不自动清除暂停。

人工恢复仅覆盖当时核实的原任务修订、摘要和暂停上下文。新的坏状态、更新的任务修订或另一个暂停原因，会产生新的暂停身份；旧回执不能解除它。已经解决原因的迟到快照也不能替换当前新的暂停。

恢复成功后，若每日或总配额已用尽，仍然不能自动安装；grant 到期、窗口外或模式为 manual 时，也继续禁止新的自动任务。重新选择自动模式或配置新的权限，是另外的决定。
