# OpsArk 运行与受控接入

当前版本采用 Python 3.13、FastAPI、Pydantic、SQLite、Paramiko 和同源静态控制台，依赖锁定于 `uv.lock`。单实例运行一个服务进程，调查和模型解释分别限制为一次一个任务。运行两个以上 worker 会绕过进程内并发限制，当前不支持。

0.3 的控制台系统、浏览器与被管理端适配分别记录在[平台矩阵](PLATFORM_SUPPORT.md)。SSH 调查先确认 Ubuntu/Debian 身份、架构与工具，再执行相关检查；范围外或无法识别时停止，缺工具保留缺口。工具存在并不证明有访问权限。

0.5 的持续观察默认关闭。需先安装固定 journal 投影 helper、更新精确策略，再显式设置 `OPSARK_OBSERVE_ENABLED=true`、`OPSARK_OBSERVE_HOSTS=node-a,node-b`（替换为实际登记 ID）；`OPSARK_OBSERVE_INTERVAL` 默认为 60 秒。配置与保留范围见[持续观察说明](SECURITY_OBSERVATION.md)。要在本机离线后仍采集，使用[VPS 常驻部署](../deploy/observer/README.md)，浏览器只是读取状态和告警。

0.7 的补丁执行使用独立 root 入口与修复密钥。0.9 的[预授权自动修复](AUTOMATIC_REPAIR.md)沿用 `OPSARK_PATCH_INVENTORY`、`OPSARK_AUTOMATION_POLICY`，没有新增自动启用环境变量：缺少明确 grant 不会提交自动动作。控制端 `automatic.sqlite3` 保存提交意图、配额与持续暂停，备份和迁移必须一并保留。隔离 guest 已在有限窗口和一次配额内完成真实自动单包升级及修复后验证，控制端实际重建后无重复安装或通知，并已同步切回手动修订 13；物理宿主不启用 automatic，其他故障/恢复对照分别留证。

0.10 已加入[暂停后的精确人工恢复](RECOVERY.md)，并完成[带故障注入的独立实验](RECOVERY_LAB.md)。它要求当前启用且授权的部署策略、已同步 manual 模式、已经 verified 的原自动任务及完整证据；确认前先核验版本/服务/复扫/运行时，确认后还要取得精确 root 回执。unknown 只查原恢复 ID；恢复不安装、不重置配额、不重签 grant，也不启用自动模式。真正 failed 或旧任务缺少安装前 manifest 时继续阻断，不能通过补造记录或删暂停恢复。

0.10 当时的常驻部署记录为 **0.10.0 / manual 修订 14**，原三个目标同步完成，自动 grant 全部禁用且没有新增授权；新故障实验目标不在当时的常驻清单中。三目标 root 入口升级了九份运行源码并重绑定策略摘要，角色、令牌及可信主机记录保持；更新后各目标取得部分扫描，不能解读为全量漏洞已清除。当前部署版本与模式应从实际实例核对。

仅升级 Web/控制端不保证远端支持人工恢复。管理员应在没有活动或未知安装事务时审核升级 root helper，再将实际返回的 source/policy 摘要更新到部署登记；旧摘要不得复用。`automatic_recovery=true` 只表示控制端有接口，逐目标可用性以真实预览为准。恢复审计保存在 `automatic.sqlite3`。当前备份和迁移应完整保留十个登记数据库，并单独保管远端 root 原任务/恢复回执及私有配置，按[发布与恢复检查](RELEASE_CHECK.md#十库恢复演练)执行。

上述 VPS 部署使用的 Compose 文件顺序为 `-f compose.yaml -f compose.lab.yaml -f compose.release.yaml`：第二份保留 guest 私网，第三份保留已审核的构建镜像选择。重建已有实例时应核对并保留该部署实际使用的 override。部署端 override 的保留要求见[常驻部署说明](../deploy/observer/README.md#可选漏洞观察与补丁入口)。

## 本机运行

```console
uv sync --locked
uv run uvicorn opsark.main:app --app-dir src --host 127.0.0.1 --port 8010 --workers 1
```

从 `http://127.0.0.1:8010/` 打开控制台。默认数据目录为仓库下 `data/`。首次启动生成 `access-token`，在本机读取文件并输入令牌即可登录。Linux 上新建数据目录和令牌文件分别限制为 0700 与 0600；Windows 部署者需要同时检查目录 ACL。

令牌不进入浏览器持久存储，API 使用 Bearer 请求头认证。API 不支持 query token；服务只接受本机 Host，写请求拒绝不匹配的 Origin。当前配置用于本机访问，不提供公网域名、TLS 反向代理或多用户部署验收。

| 环境变量 | 用途 |
| --- | --- |
| `OPSARK_DATA_DIR` | 数据目录，默认 `data/` |
| `OPSARK_TOKEN` | 可选部署令牌，至少 32 字符；未设置时使用本机生成文件 |
| `OPSARK_INVENTORY` | 可选 SSH 主机清单的绝对路径；未设置时只提供样本回放 |
| `OPSARK_PATCH_INVENTORY` | 既有目标、独立修复私钥文件及当前远端策略摘要的 JSON 引用 |
| `OPSARK_AUTOMATION_POLICY` | 控制端执行策略 JSON 引用；可含独立的自动 grant，默认没有自动授权 |
| `OPSARK_AI_PROVIDER` | `openai` 为默认兼容接口，`anthropic` 为 Claude Messages 原生接口 |
| `OPSARK_AI_BASE_URL` | 可选兼容接口的基础地址，例如提供方的 `/v1` 路径 |
| `OPSARK_AI_KEY` | 模型提供方凭据，通过服务进程环境或部署系统的秘密管理注入 |
| `OPSARK_AI_MODEL` | 提供方实际支持的模型标识，由部署者选择 |

应用不自动读取 `.env`。配置环境变量后重启服务。API 从不返回令牌、模型凭据、私钥正文或凭据文件路径。

## 回放调查

登录后默认选择本地合成样本。12 份 JSON 原始检查样本覆盖端口不一致、上游停止、容量与 inode、OOM 与未知退出原因、认证事件以及健康和权限缺失对照。

运行调查会实际执行解析与诊断规则，并将新报告写入 SQLite。报告来源为 `replay`；证据时间是样本读取时间，不是服务器实测时间。页面刷新重新登录后可继续查看历史，列表最多显示最近 100 份，旧报告不会自动删除。

打开已保存的报告，可选择「导出内部报告」或「下载客户交接摘要」。交接摘要使用文档内的证据序号，只列出已分类的事实和检查结果。旧报告中未分类的文字只计数，主机信息、原始日志和 AI 自由文本留在内部报告。回放摘要标注合成数据，即时检查符合时仍单独显示业务恢复未验收。

真实 SSH 调查的交接摘要可选关联一个同目标、同登记范围的补丁任务，并可附加后续只读复验记录。摘要依次展示提交授权、原任务结果、实际记录的提交结果未知及同 ID 查询对账。只有保存了原绑定且取得可信原任务状态回执时才展示对账完成。旧任务缺少这份绑定时，仍可导出调查摘要。

在交接窗口选定补丁任务后，点击「运行只读复验」。已登记 `business_checks` 时，目标机比对业务响应，控制台只保存与原调查、任务、审批和当次检查登记绑定的状态回执。旧版复验报告仍可选择和导出。窗口会选中新结果，显示验收状态、符合项数和采集时间，最多展示最近 20 条符合条件的记录。某次调查和任务已经使用新回执后，即使移除这份登记，也不会退回旧版正文采集。

导出读取本地已保存的记录。复验须在原任务验证、对账或关联的服务激活形成的最新验收边界之后开始。明确失败显示「复验未通过」，只有通过和证据不足时仍显示「待验收」，全部登记项通过才显示通过。新的对账边界会让较早的回执保留为待验收。新回执不采集原始日志，业务正文留在目标机，回执不进入调查报告或模型入口。客户摘要只列出状态、时间和符合项数。[隔离环境实机验收记录](HANDOFF_LAB.md)

0.2 样本还包含合成的站点检查结果。先调查“容器状态正常对照”，在报告中确认保存观测基线，再调查“容器 OOM”，可查看模拟字段变化。保存基线不重写当前报告，后续比较仍分别标注来源和覆盖缺口。

## 登记 SSH 主机

打开「已登记主机 → 准备接入新主机」。通过云厂商控制台等可信渠道取得目标的公开主机密钥与 SHA256 指纹。例如在可信目标控制台核对 Ed25519 公钥时，可运行：

```console
cat /etc/ssh/ssh_host_ed25519_key.pub
ssh-keygen -l -E sha256 -f /etc/ssh/ssh_host_ed25519_key.pub
```

向导接收一行 OpenSSH `.pub` 公钥和独立核对的 `SHA256:…` 指纹。核对一致后，复制生成的 TOML 和 `known_hosts`。使用向导给出的路径，把已有专用只读账号的登录私钥放在控制台部署机的私有目录，并按部署说明限制权限。`known_hosts` 单独保存为无 BOM 的 UTF-8 文本。相对路径均从清单所在目录解析。合并清单前核对主机标识，避免重复登记。

应用清单并按部署流程重新加载控制台后，从对应主机卡片运行接入预检。当前已加载的主机地址、端口和可信主机文件都与向导产物匹配时，向导提供跳转到原预检入口。生成材料本身不读写部署文件或连接 SSH。

不知道真实容器名时，可先授权一个 Compose 项目并省略容器名。生成材料会标记 `container_binding_confirmed = false`，容器保持待确认，既不采集占位容器状态/日志，也不生成这些命令的权限。管理员应用清单及精确只读策略后，可在主机卡运行[授权项目的候选发现](COMPOSE_DISCOVERY.md)，明确选择 TCP 发布端口并重新核对；网页只生成登记片段，不自行保存或执行。Nginx 依赖关系仍须另行核对。

要自动观察普通宿主 Nginx 与这些候选之间的关系，部署者可按 [Nginx 本机依赖发现](NGINX_DEPENDENCIES.md)单独登记 root 拥有的读取范围、原始 scope SHA 和无参数 helper。网页不接收配置内容或路径。当前只证明所见磁盘指令与当时本机发布端口的关联，已加载配置代次和业务验收仍未知，所有动作保持关闭。

也可手动登记。

以 [opsark.example.toml](../opsark.example.toml) 为模板，保存到私有的 `opsark.local.toml`：

1. 在受控的执行环境保存专用 SSH 私钥，使用服务进程可读取的最小文件权限。
2. 通过可信渠道核验服务器主机指纹，建立独立的 OpenSSH `known_hosts` 文件。非 22 端口使用 `[IP]:端口` 记录。应用不自动接受未知密钥。
3. 在 `credentials` 中登记已有文件的引用；路径相对清单文件解析，也可以使用绝对路径。
4. 登记唯一的主机标识、IP、端口、专用非 root 账号和站点域名；填写已确认容器，或限定 `compose_project` 并明确 `container_binding_confirmed = false`，先进行只读发现。
5. 设置 `OPSARK_INVENTORY` 并重启。控制台显示“已登记”，这不表示已经成功连接。

在「已登记主机」中点击「运行接入预检」，可核对 SSH 连接、适配器与工具、Nginx 和登记容器的运行状态、根分区容量和 inode，以及 Compose v2 插件与本地 rootful Docker 引擎，共八项固定检查。插件使用固定 `docker compose version --short`，仅接受完整、可解析的 major 2 版本；引擎使用固定 `unix:///var/run/docker.sock` 的受限 `info --format`，仅提取 Linux 类型和安全模式，检测到 rootless 不算通过。不会执行 Compose 项目、读取 Compose 配置、安装插件或修改登记。

只有八项完整通过才为 `ready`；缺插件信号、其他版本、权限不足、固定策略拒绝、超时、截断和无法分类的输出分别保留固定缺口，不显示原命令输出或异常文本。旧服务器策略没有这两条新命令时，管理员须重新导出、审核并安装精确只读策略；页面不会自动扩大权限。预检沿用登记的凭据和可信主机记录，不调用模型，不生成调查报告或观测基线。它只证明这些固定检查在当时可用，不证明 Compose 项目能够部署、自动依赖已经发现或业务已恢复；实际业务路径另用「运行只读业务检查」核对。

命令与判断依据见 Docker 官方 [Compose 版本命令](https://docs.docker.com/reference/cli/docker/compose/version/)、[引擎信息格式](https://docs.docker.com/reference/cli/docker/system/info/)及 [`name=rootless` 安全模式字段](https://docs.docker.com/reference/api/engine/version-history/)。本项本地合成验证与标准 VPS 的真实接入验收分别记录，不扩充旧实验的通过范围。

目标由清单控制，API 不接受新目标、私钥内容、任意文件路径或 Shell。为避免 DNS 解析和多地址尝试超出连接预算，当前只接受 IPv4 / IPv6 字面地址。

首批检查假定宿主机 Nginx，错误日志为 `/var/log/nginx/error.log`，服务名为 `nginx`；容器由登记名称选择。Docker CLI 显式指定目标机器的 rootful 本地 socket，并去除远程 context 与 TLS 环境覆盖。Rootless、自定义 socket 和容器内代理需要后续适配。

容器 inspect 仅请求诊断字段。`State` 显式限定为 `Status`、`Running`、`OOMKilled` 和 `ExitCode`，不请求完整状态对象、健康检查输出或运行时错误正文，也不读取环境、启动命令和入口参数。该精确命令发生变化时，部署者须重新导出并审核安装目标只读策略；控制台不会自动改策略或放宽服务器权限。

应用只发出固定的状态、日志和占用读取命令，不主动安装组件或更改远程权限。普通 Docker 用户组本身具有 root 级能力，不能把“非 root 登录”当作完整的 OS 权限隔离。

0.4 提供由管理员安装的[服务端强制命令入口](../deploy/readonly/README.md)：专用账号不加入 Docker/journal 组，SSH 公钥被强制绑定到严格查表的 sudo helper，helper 只执行 root 所有策略中的固定 argv，限制时间、输出和单机并发。应用发出的命令形式保持不变；只有实际安装并完成拒绝验收的服务器才具备这层限制。两台授权 VPS 的实际验收见[实机记录](VPS_LAB.md)。没有安装该入口的目标仍只有应用内的命令限制。

### 业务就绪检查

在对应 `[[hosts]]` 下登记最多三个 `[[hosts.business_checks]]`。选择经过审核、无副作用的本机 HTTP GET 路径，给它设置一个稳定、可公开的预期响应。用预期的完整字节计算 SHA-256，例如 `printf '%s\n' 'opsark-origin-main' | sha256sum`。换行属于响应字节。

```toml
[[hosts.business_checks]]
id = "application"
domain = "shop.example.com"
port = 8080
path = "/public/readiness"
expected_status = 200
expected_body_sha256 = "<预期完整响应的 64 位小写 SHA-256>"
read_only_confirmed = true
```

此检查要求 `opsark-readonly` 账号、重新导出的目标专属策略和新版[只读安装器](../deploy/readonly/README.md)。目标机的降权进程访问自身 IPv4 回环 HTTP 监听器，在本地比对最多 8 KiB 完整正文。SSH 只传状态码和匹配结果。控制台只展示登记标识与结果，业务正文、响应头和摘要均不进入控制台历史或模型请求。同一路径不能同时登记到会采集正文的 `health_checks`。

有效的状态码或正文不符显示失败，超时、证据不完整或目标机缺少新工具显示待确认，未登记或未确认只读显示未覆盖。全部登记项通过才显示通过。此检查覆盖本机代理路径，不包含公网 TLS、DNS 或 CDN。[HTTP/1.1 消息边界](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)

隔离测试机使用实际 Nginx、只读安装器和受限 SSH 验收。静态探针始终通过时，业务路径返回 502 或由错误上游返回 200 均显示失败，恢复到正确响应后通过。SSH 回执和 API 只含登记状态，原始正文未外传，控制台历史和模型调用均无变化。可从源码仓库运行 `tests/business_readiness_lab.py` 复验。

### 隔离 SSH 防护动作回查

此项用于完整源码仓库中的隔离实验，实验执行资产 `deploy/defense/` 不随私有候选包分发。完整步骤请从源码的 `deploy/defense/README.md`「控制台只读回查」章节取得。实验可在对应 `[[hosts]]` 中登记 `ssh_defense_action_ids`，最多八个原动作编号。当前只接受 `198.18.241.2:22423` 和 `opsark-readonly` 账号。目标机策略逐个固定允许的编号。主机页先读取登记列表，再由用户点击一次状态查询。

观察记录保存在既有 `security.sqlite3` 中。当前连接不可用或目标返回未知时，历史状态会单独标注。控制台不会根据旧剩余时间自行判定已到期，目标主机指纹变化后也不会套用旧观察。此接口只执行只读回查。

## 采集预算与结果

- SSH 连接、banner 与认证各设置 4 秒超时；私钥和主机文件来自部署者登记的本地路径。
- 连接建立后，整组检查使用 25 秒预算，单项最多 7 秒；远端命令额外使用 5 秒 `timeout` 和 1 秒强制终止宽限。这些预算不是生产响应 SLA。
- 单个检查的 stdout 和 stderr 合计最多读取 16 KiB，达到限制即截断并关闭检查通道。
- 日志只取最近指定条数，目录扫描限于固定目录并受超时限制。失败或部分 journal 权限会明确记录，不当作没有异常。
- Docker 应用 stderr 在 CLI 成功时作为日志内容参与分析，CLI 执行失败则保留失败状态。

来源、状态、截断和证据缺口会随报告持久化。单次采集不提供历史变更或增长速度。当前支持登记站点的即时只读检查，不执行配置语法检测、修复或完整恢复验收。

证据时间记录本组采集的开始时间，各检查不是跨服务的原子快照。发生快速变化时，需要补充时间关联与连续观察。

## 登记站点检查与配置摘要

在对应 `[[hosts]]` 之后增加 `[[hosts.health_checks]]`，字段参考样例清单。每台主机最多三项，标识唯一；域名用于 Host 头，端口和静态路径用于该主机自身的 IPv4 loopback 请求。部署者需要先确认指定 GET 没有业务写入，再设置 `read_only_confirmed = true`。GET 方法名称本身不保证无副作用。

检查固定使用 `/usr/bin/curl --disable`，忽略账号 curlrc，禁用代理且不跟随跳转；不接受临时 URL、认证头、查询参数或请求体。连接 2 秒、curl 总时长 4 秒、正文上限 8 KiB，仍受整组采集预算和输出截断限制。失败、超时和正文不符合分别显示，不能以正文中出现“200”替代实际尾部状态码。先在原始受限响应的内存结果上比对，随后仅保存脱敏证据和状态/条件布尔值，脱敏替换文字不参与成功判断。

即时检查只说明登记条件在本次观测中的表现，不覆盖公网 DNS、TLS、CDN、登录、下单或支付。即使显示“即时检查符合”，完整恢复验收和持续观察仍保留原状态。

正文核验使用 UTF-8 / ASCII 文本，非法编码记为检查未完成，不用解码替换字符作成功依据。请求明确要求 identity 编码；建议登记无歧义的业务标记，字面包含某个短词本身不证明业务正常。

`nginx_config_path` 可选配置 `/etc/nginx/sites-available/` 或 `/etc/nginx/conf.d/` 下的单个安全文件名。只采集 SHA256，不传输配置正文；最终路径是符号链接时拒绝。摘要不是原子快照、已生效配置或可恢复备份。

## 保存与比较观测基线

在新报告中选择“保存为观测基线”，明确确认仅作观测对照。基线从该报告的完整、成功且可解释的证据提取字段，不接受客户端上传字段或任意原始日志。保存于 `data/baselines.sqlite3`，原报告保持不变。

支持的字段包括系统版本、登记容器状态/镜像/端口/资源限制、根分区容量与 inode、Nginx active 状态/登记文件摘要，以及 HTTP 状态与正文条件是否满足的布尔值。HTTP 字段使用已验证并与证据绑定的安全元数据，缺失或矛盾时保留缺口。基线不保存响应正文或匹配文本。

后续调查按来源、主机、场景选择最新基线，并核对登记范围摘要。目标地址、端口、容器、检查条件或可信主机记录变化时停止沿用旧范围。SSH 可信记录在采集前也会重新核对，变更后需要重新加载登记。失败字段不能当作零或正常，缺失与新增字段会保留为对照缺口。

当前差异引用本次证据，旧值可跳回基线报告复核。基线保存时间不等同于变化发生时间；两个观测之间有差异不直接证明修改者、部署原因或因果关系。基线用途固定为 `observation_only`，`restore_capable` 固定为 `false`。

旧报告没有范围和目标元数据时不能直接建立基线，需要新调查。升级保留原报告，新增数据库不改变旧报告的采集事实。

基线包含字段算法版本。缺少当前版本的早期开发基线不再参与比较，旧记录保留，需从新调查重新保存，避免沿用旧的 HTTP 派生判断。

### 容器调查业务复验

有已登记并确认的只读业务检查时，从新建的 SSH 容器调查进入「恢复验收」，在「容器调查业务复验」选择「运行容器调查只读复验」。有明确失败时显示「复验未通过」。超时、未覆盖或缺少已认证的检查证据时显示「待验收」。只有全部登记项通过才显示「复验通过」。

恢复业务后回到同一份报告再运行复验。在「容器复验快照」选择要查看的历史结果，下载该次脱敏摘要。若提交响应中断，先刷新历史，再用「重试原容器复验」取回已保存的结果。旧报告未绑定业务检查或目标登记变化时，重新运行一次容器调查以取得新绑定，先前结果仍可读。

## 可选模型解释

基础地址、凭据和模型名需要同时设置。默认 `OPSARK_AI_PROVIDER=openai` 使用 `/chat/completions`，可配置 OpenAI、DeepSeek 等提供的兼容地址。Gemini 的兼容前缀为 `https://generativelanguage.googleapis.com/v1beta/openai`，可从 `json_prompt` 配置开始。兼容服务的模型名和参数按对应供应方文档核对。远程接口使用 HTTPS，HTTP 仅用于控制端本机的 loopback 服务。[Gemini 兼容接口](https://ai.google.dev/gemini-api/docs/openai)

使用 Claude 原生接口时，设置 `OPSARK_AI_PROVIDER=anthropic`、`OPSARK_AI_BASE_URL=https://api.anthropic.com/v1`、`OPSARK_AI_RESPONSE_FORMAT=json_prompt`、`OPSARK_AI_TOKEN_LIMIT_PARAMETER=max_tokens` 和 `OPSARK_AI_THINKING_MODE=provider_default`。模型名选部署者在 Claude API 可用的标识，API 密钥由服务端配置。该模式使用固定官方 `/v1/messages` 地址。[Claude Messages 接口](https://platform.claude.com/docs/en/api/messages/create?version=2023-06-01)

选择报告后，用户在界面主动确认才发送数据。所有提供方复用同一个外发门禁，只允许分类结果、计数和临时证据编号等白名单摘要。凭据、数据库原文或无法分类的内容触发整次拦截。Claude 格式转换只接收已通过门禁的正文。请求使用部署者指定的一个提供方，关闭重定向、环境代理、自动重试和供应方切换。确认绑定所见报告，切换目标后需要重新确认。响应必须通过本地 JSON 结构与证据编号校验，报告解释最多读取 32 KiB，失败时保留原诊断。[安全边界](SECURITY_MODEL.md#模型输入与数据保留)

选择的 JSON 输出方式仍需通过本地结构校验。新增接口的协议、拒绝路径与数据边界使用隔离环境中的模拟提供方验证。[OpenAI 结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)

## 数据与部署

已实现对常见认证头、Cookie、命名秘密字段、已知令牌形式、私钥块及多种 URL userinfo / 查询参数的脱敏，再保存报告。它不是任意日志中所有个人信息和秘密的识别保证；真实接入应限制日志范围，并验证实际样本的脱敏覆盖。

报告和访问令牌保存在本机数据目录，Git 默认忽略数据、私有清单、环境文件与常见密钥。观察缓存分别有数量限制；调查历史及审计备份没有统一自动清理，模型来源与执行身份账本达到容量上限会拒绝新增并保留原件。当前没有账户隔离。部署者负责数据目录访问、保留与删除；备份时停止服务并处理整个数据目录，不以复制单个运行中的 SQLite 文件作为恢复保证。当前传输工具保留十个数据库（包括 `automatic.sqlite3` 和 `vulnerability-ai.sqlite3`）；激活记录复用 `patches.sqlite3`。完整列表和 SQLite backup/manifest 约束见[常驻迁移说明](../deploy/observer/README.md#迁移与停止)。令牌、env、密钥和远端 root 审计分别保留，不把它们放入公开传输清单。

Docker Compose 默认将服务发布到 loopback，容器以非 root 用户、只读根文件系统运行，数据卷可写，不挂载宿主 Docker socket。要启用 SSH，需另行提供只读清单及秘密挂载，并设置容器内 `OPSARK_INVENTORY`。Ubuntu CI 已构建运行镜像并验证认证接口与重启后报告持久化；这些结果不替代目标 VPS 的故障实验。

## 容器、镜像与 Compose 配置变化

管理员可为一台已登记的 SSH 主机启用此观察。先按[目标机安装步骤](../deploy/readonly/COMPOSE_GENERATION.md)登记同一个容器名、Compose 项目和服务，核对范围 SHA-256，并重新导出和审核该主机的只读策略。控制台清单使用下列字段，摘要取目标机已审核范围文件的 SHA-256。

```toml
compose_generation_service = "web"
compose_generation_scope_digest = "<64 位小写十六进制范围摘要>"
```

做一次真实 SSH「容器重启」调查并保存为观测基线。再次调查后，在「观测基线与变化」中选择「查看容器与 Compose 配置变化」。只有调查前后的目标、守护进程和观测结果一致，控制台才会保存本次比对记录。它会分别标记容器实例、镜像和 Compose 配置的变化。缺少可比观测、目标机换钥或 Docker 重启时，界面保留证据缺口。配置对照要求两次观测均有同版本 Compose v2 标签。

比对只使用目标机生成的私有记录，部署来源、变更时间和操作者仍显示未知。客户摘要、调查导出和 AI 请求均不包含这些记录。

## 资源占用与小型 VPS

2026-10-31 已补齐[完整1核/1GiB KVM容量验收](CAPACITY_ACCEPTANCE.md)：OS、Docker、控制台、Root扫描/真实单包补丁和普通服务激活均放入同一客体预算，一小时无OOM/swap，可用内存最低约282MiB，控制台独立峰值约77MiB。结论限指定轻型负载，512MiB、数据库及多目标并发仍未验收。可选Ubuntu Pro子进程现有固定256MiB虚拟地址空间预算，超预算显示部分覆盖，独立官方USN依据保留。以下10月29日组件数据继续按原范围保留。

2026-10-29 实测环境为两台 4 核、约 7941 MiB 内存的测试 VPS。模型使用远端兼容 API，未在 VPS 本地运行模型，因此不需要本地 GPU 或大模型显存。以下区分常驻控制台、临时实验和包管理开销，不把配置上限当最低要求。

| 对象与测量范围 | 观测值 | 结论边界 |
| --- | --- | --- |
| 0.15 常驻控制台，3 个登记目标持续观察 | 当前约 81–91 MiB，容器累计峰值约 102 MiB；60 秒 CPU 均值约 2.04% 单核 | 短窗口、有限目标，不是长期高并发压力结论 |
| 0.16 升级后的同一常驻控制台 | 当前约 80 MiB，容器累计峰值约 109 MiB，OOM 事件为零 | 升级后短窗口，不能替代长期容量测试；旧实验服务另约 226 MiB，不属于该控制台自身 |
| 0.16 独立控制台容器，硬限制 128 MiB / 0.25 核 / 无 swap | 启动、认证、12 样本列表、一次合成回放及导出通过；峰值 71.2 MiB，无 OOM | network=none、无 SSH/模型/真实扫描/补丁；不是整台 512 MiB VPS 验收 |
| 新 systemd 实验 guest | 累计峰值约 198–242 MiB，包含环境准备、APT/python-apt 采集与单包补丁等阶段；未出现 OOM | 取 Docker 容器根 cgroup，包含系统服务和缓存；不能说成单个 helper 的净增量，也不是各阶段独立峰值 |
| 常驻数据 / 历史审计备份 | 约 15.6 / 165.4 MiB | 历史备份与开发演练额外占用，数据会继续增长 |
| 0.16 控制台镜像逻辑大小 | 约 82.8 MiB | Docker 层可共享，不等于服务器全部镜像、缓存和日志磁盘占用 |

被管端通过固定 SSH 入口按需运行，普通接入不需要每台再运行一整套控制台、实验 guest 或本地模型。APT 索引/归档本次每台另占约 300 MiB 磁盘；它们属于系统包管理数据。历史实验的额外 controller 和 guest 单独列入私有测量，不能把它们都算作正式部署的必需资源。

观察投影的有限保留不等于所有磁盘数据都会自动回收。执行身份、模型原始来源和 Root 审计用于避免重复动作及事后核对，不能按普通日志直接覆盖；容量规划需同时覆盖归档、备份和容器日志。

**1核/1GiB已完成上述受控轻型负载验收**，同机数据库、更多网站和日志仍需另留余量，不是所有环境的最低规格保证。512MiB基础控制台有可行性，但完整512MiB OS、Docker、APT及业务同机尚未验收；更小目标宜先把控制台放到另一台机器，仅保留受限SSH。并发、长期增长和更多包需要独立验收。

测量方法：只读 `/proc`、Docker metadata/stats 和容器根 cgroup（含 systemd 子组），60 秒序列每 2 秒采样，累计 peak 不重置。PID1 的 `init.scope` 叶子不代表整个 guest，早期此类原始样本保留但未用于上述整 guest 数据。容量实验使用冻结镜像、独立数据和 token、无网络/端口，完成后停止并删除临时 token；未新增真实模型、扫描、安装或服务动作。私有容量验收原件包括 snapshot、series 与 `limited-console-128MiB.safe.json`。

guest 的上述资源样本截至单包补丁完成，不是对后续每个激活阶段的连续采样。常驻 0.16 新样本另存于 `after-main-016/`，未覆盖早先原件。旧演练服务包含测试专用控制端和 guest；本轮新增的两套激活实验环境已按各自收尾记录停止。正式部署不需要复制这些故障实验环境。
