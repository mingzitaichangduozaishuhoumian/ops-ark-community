# OpsArk 产品计划

更新日期为 2026 年 11 月 4 日。

OpsArk 帮助维护多个网站的小团队判断服务器异常、进行有限的安全响应，并验证处置后的业务状态。第一版围绕普通 VPS 上的 Nginx 和 Docker Compose，建立从网站到依赖、证据、动作和验收结果的完整记录。

当前为实施基线，用户需求、接入意愿与使用频率仍需通过真实任务验证。

## 用户与核心问题

首批用户选择替客户维护网站的个人开发者、建站工作室和小型外包团队。个人站长可参与试用。优先接触近期处理过网站故障、能提供脱敏案例并愿意连接测试机器的用户。

| 用户问题 | 产品输出 |
| --- | --- |
| 客户说网站挂了，排查入口不明确 | 域名对应的主机、代理、容器与依赖，以及缺失的映射 |
| 多种异常同时出现，无法判断原因 | 事实、候选原因、反证、缺失证据与下一步检查 |
| 修改可能影响其他网站 | 目标对象、共享依赖、受影响站点与动作预览 |
| 不确定是故障、攻击还是防护误伤 | 资源、配置、流量与安全事件的关联时间线 |
| 处理完需要验收和交接 | 业务检查、观察结果、未解决事项和可导出的事件报告 |

产品价值首先看用户能否更快完成查证和验收，以及是否愿意再次使用。持续安全观察和变更记录能否增加使用频率，作为待验证假设。

## 定位与差异化假设

主张是“针对具体网站，有证据地诊断、有限地处置、按业务标准验收”。

重点验证以下组合是否值得用户迁移或增加一个工具：

- 适配已经运行的网站，建立域名、主机、Nginx 与 Compose 服务的依赖关系。
- 联合调查运维异常和安全事件，说明目前能够证明的原因与仍未知的部分。
- 检查处置是否影响正常用户、共享服务和相关站点。
- 根据实际采集结果生成便于客户交接的事件记录。

公开产品已覆盖 AI 排障、SSH 接入、审批和自动封禁。市场机会在于特定用户的工作流和适配效果，不能将上述单项功能宣传为首创。

## 首批环境

以下为拟验证环境，尚未形成支持承诺。

- 先固定 Ubuntu 24.04 LTS 虚拟机，完成单机 Nginx 加 Docker Compose v2 的验证；随后增加 Debian 验收环境，并记录具体版本。
- 首批 Nginx 运行于宿主机，Compose 服务运行于同一台 VPS；容器内代理、多层代理与多机依赖后续单独验收。
- 故障诊断通过专用 SSH 接入；持续防护优先接入 CrowdSec 等现有组件的事件与结构化动作，避免重复建设检测引擎。首个拟接入组件为 CrowdSec。
- 控制台支持自部署，部署方案应允许与被管理 VPS 分离。
- 已有面板管理的主机先进行只读适配。配置归属和写入冲突未经验证时，不启用修改动作。

## 故障诊断范围

| 场景 | 首批检查与结论 | 处置边界 |
| --- | --- | --- |
| 网站 502 | 域名到已登记源站、Nginx 状态与语法、上游地址和端口、容器状态、相关日志和可追溯变更 | 优先交付证据；后续支持经预检的 Nginx 配置重载。应用代码缺陷交付开发者排查材料 |
| 磁盘空间异常 | 文件系统容量与 inode、目录占用、日志和业务数据分类；存在历史样本时分析增长 | 先提供可清理对象及有依据的容量估算；业务数据、数据库文件和持久化卷不自动删除 |
| 容器反复重启 | 退出和重启记录、资源限制、健康检查、应用日志、配置与镜像变化 | 区分已知事实与推测；停止、重启或重建容器逐次审批，注明状态与数据影响 |

近期变更只引用已保存的基线、部署记录或用户提供且标明来源的信息。首次故障接入时没有历史记录，应显示无法追溯的时间范围。

恢复动作要分别说明临时缓解和根因修复。短时可访问不能直接作为彻底解决的结论。

## 安全响应范围

| 场景 | 首批输出 | 自动化顺序 |
| --- | --- | --- |
| SSH 暴力登录 | 可信来源、失败与成功登录事件、受影响账号和触发规则 | 观察与告警，通过验证后开放预授权的短时来源封禁 |
| 网站异常请求 | 站点、路径、规则、请求变化与业务影响；区分可疑行为和已证实事实 | 先记录建议动作，随后在已验证组件上开放有限封禁或限流 |
| 防护疑似误伤 | 新规则与合法访问失败的时间关系、受影响业务、撤销建议 | 支持撤销具体新规则，保留其他既有防护 |

陌生账号、密钥、计划任务、进程或容器的变化发现列入后续调查能力。首版不承诺自动清除入侵、抵御所有未知漏洞或由单台 VPS 解决上游带宽耗尽。

自主防御的范围限定为用户授权管理的资产及接入的防护服务。主机隔离、凭据轮换和系统恢复进入单独的审批与恢复流程。

自主漏洞修复列为核心主线：采集本机软件与配置，关联发行版官方漏洞及修复数据，确认实际受影响后生成计划，按手动、半自动、全自动模式处理，再复扫并验证服务。首个执行通道为 Ubuntu 官方 APT 安全单包升级，隔离 guest 的半自动真实闭环已有验收；0.9 另完成一次受限预授权自动升级及复扫、运行时、HTTP、新 SSH 验证。控制端与 root 分别约束包/USN、UTC 窗口、期限、次数、风险与暂停，首轮只给隔离 guest 有限的一次授权，物理宿主禁用。控制端重建防重复及同步切回手动已验收，失联、到期和恢复流程等对照仍待开展；后续扩展容器镜像、应用依赖和恢复流程，详见[实施合同](VULNERABILITY_REMEDIATION.md)及[自动修复边界](AUTOMATIC_REPAIR.md)。

## 网站接入与使用流程

1. 登记客户或项目、主机和网站，验证 SSH 连接和可用权限。
2. 自动识别依赖，展示域名、Nginx、Compose 服务和共享资源；不确定的映射由用户确认。
3. 登记业务检查地址、预期状态或内容，以及观察窗口。首版自动验收限定为无业务写入的检查；未配置的业务环节明确标为未覆盖。
4. 建立初始基线，展示采集覆盖、权限不足、历史缺失和敏感数据处理范围。
5. 通过手动检查、提交域名、接收既有告警或本地安全事件启动调查。
6. 展示事实、候选原因、缺失证据与动作影响，检查对应授权后执行。
7. 验证动作生效、目标业务和相关依赖，持续观察并生成事件记录。

界面先围绕五个工作区设计：网站与主机、事件列表、调查详情、动作与授权、验收与报告。聊天用于补充信息与解释，关键事实和动作保留结构化记录。

## 证据与验收结果

每条证据包含目标、来源、采集时间、结果引用、采集是否成功和脱敏情况。报告区分采集事实、用户陈述、候选原因和未覆盖范围。

每个事件使用“调查中、待处置、执行中、初步恢复、观察中、已验收、未解决”等状态。执行失败、失联或证据不足都保留独立记录，不得自动标记为恢复。

验收同时回答：

- 动作是否按授权执行，规则或配置是否实际生效？
- 原异常是否减轻，是否仍有新的错误或重启？
- 目标业务检查是否通过，相关站点与共享依赖是否受影响？
- 对已有观测数据或单独授权的测试，正常登录、业务回调等合法请求是否被误伤？未验证的环节是否已标明？
- 观察窗口内是否稳定，是否仍需人工处理？

报告可导出给客户或开发者，内容包括时间线、证据、动作、授权、验收与未解决事项。正式报告不把推测写成事实。

## 后续方向与取舍

变更预检作为执行链的一部分，包含差异、确定性检查、配置备份、影响判断和回退条件。配置恢复与业务数据恢复分别设计，不统一承诺一键回滚。

环境盘点和交接复用同一份采集证据。控制端加密备份和隔离恢复已有实机验收。业务数据库与持久卷恢复单独验证，先限定数据库类型、备份方式和恢复环境。通用 Agent 执行平台、完整 WAF、EDR、SOC、多云和 Kubernetes 管理不进入首版。

### 接单与验收

标准环境为 Ubuntu 24.04 x86_64 VPS、宿主 Nginx 和 rootful Docker Compose。每个客户使用独立控制台。预检先确认可达性、主机指纹、客户管理权限、已登记业务检查和备份接收端。兼容性或资源证据不足的环境转为专项评估。[平台范围](PLATFORM_SUPPORT.md) · [资源验收](CAPACITY_ACCEPTANCE.md)

- 部署验收包括认证、受限 SSH、报告持久化、登记健康检查和备份清单。防泄密用合成输入校验。客户自行保管生产凭据和解密钥，支持过程使用客户授权的专用受限账户或由客户执行核准命令。
- 维护范围包括已登记 OpsArk 组件、采集和告警链路。补丁与服务激活限于经核验的 Ubuntu 单包安全更新和普通服务。补丁、激活和暂停解除分别核对目标、影响、批准及验证结果。结果未知时保留暂停并查询原 ID。[恢复约定](RECOVERY.md)
- 套餐中的备份与演练范围为 **OpsArk 控制端**。备份检查记录最新归档时间和校验结果，缺少可校验副本时在含时内经授权补做一次。归档核对配置、镜像、十库和权限清单，数据在源端加密。恢复在断网副本中核对历史、模式和只读接口。目标机的 Root 账本在接单时单独列明保留和验收范围。[控制端部署说明](../deploy/observer/README.md#迁移与停止)
- 业务数据库及持久卷恢复、站点迁移、应用开发、入侵取证、DDoS 清洗、跨平台写入和全天值守进入专项评估。控制台持续观察产生告警，人工支持按上述时段处理工单。
- 交付或结束维护时交还部署版本、资产范围、运行手册、最新备份和验证结果、待办与未覆盖项。确认客户可自行接管后，撤销服务方临时访问并按约定清理留存。

### 试点验证

先接受协助部署和基础维护，工作室维护按预约提供。首轮最多服务 3 个客户、合计 6 台管理目标，工作室档最多 1 家。人工确认范围、报价、维护窗口和验收，应用保持现有自部署流程。支付、订单和自动续费留待试点复盘后决定。

内部估算暂按 ¥150／小时直接人工成本。协助部署按 3 小时测算约 ¥450，基础维护用满 2 小时约 ¥300，工作室维护用满 5 小时约 ¥750。这些测算另需预留沟通、排班和突发工单时间。首批 3 单后核对预检通过率、实际部署工时、例行工作和工单耗时、首次回复达标率及续费意愿，再调整范围与价格。

服务设计参考了 Plesk 将自助和专业服务工时分别列出，以及 Canonical 对支持时段、首次回复和处置进展分别定义的做法。OpsArk 上表为自己的试点价格。[Plesk 专业服务](https://www.plesk.com/professional-services/) · [Canonical 支持说明](https://canonical.com/legal/ubuntu-pro-description)
