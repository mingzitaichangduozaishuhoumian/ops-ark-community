# 上游与 inode 多故障验收

在已授权的一次性 Linux Docker runner 运行，使用固定镜像 ID。镜像需包含系统 Python、Nginx、静态 BusyBox、GNU coreutils、curl、ss 和 ldd。实验使用现有文件系统夹具，增加真实 Nginx 与 Python 上游。

```console
uv run python tests/mixed_fault_lab_smoke.py --image sha256:<固定实验镜像> --confirm-isolated
```

目标容器使用 `network=none`，只保留 `SYS_CHROOT`，内存上限 192 MiB、零额外 swap、0.25 CPU 和 32 个进程。实验根 tmpfs 的逻辑上限为 2 GiB，inode 数为 256，故障由有限的零字节文件触发。容器不挂载宿主路径或 Docker socket。PID 1 回收实验子进程，并在 300 秒后结束该命名空间。

Nginx 以固定 root 用户的单进程模式运行，使临时目录属于当前夹具用户。目标站点经真实上游返回标记，对照站点直接返回独立标记。错误日志写在实验根，配置和临时目录放在独立状态 tmpfs，并在故障前准备好。

同一个登记主机和 SSH 指纹下，正常调查 API 分别采集 `web_502` 与 `disk`。所有已执行命令都固定映射到同一容器的 chroot，使用原始 GNU 输出和真实 HTTP 响应。缺少的 systemctl 和 Docker 工具保持不可用，不补造服务或容器状态。

| 阶段 | 目标 HTTP | 对照 HTTP | inode |
| --- | --- | --- | --- |
| 正常对照 | 200 | 200 | 可用 |
| 两项故障 | 502 | 200 | 实际 ENOSPC |
| 仅恢复上游 | 200 | 200 | 仍然耗尽 |
| 仅恢复磁盘 | 502 | 200 | 已释放 |
| 最终恢复 | 200 | 200 | 可用 |

实验核对两个场景的基线和十份历史报告。inode 候选只引用 inode 证据，连接拒绝事实引用真实 Nginx 错误。保留旧错误日志，恢复后的网页报告仍可能需要关注。当前 HTTP 检查、历史日志和完整业务恢复分别按已有证据判断。

2026 年 11 月 5 日，授权测试机完成五个阶段的实测。仅恢复上游后仍保留 inode 异常，仅恢复磁盘后目标仍为 502，对照站点始终为 200。十份历史报告逐字节读回一致，独立磁盘实验也在同一版本夹具上复跑通过。临时容器、镜像和依赖环境已清理，原有容器与网络核对一致。
